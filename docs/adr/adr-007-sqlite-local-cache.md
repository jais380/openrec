# ADR 007: Selection of Native SQLite3 with WAL and Synchronous = NORMAL over SQLModel ORM and CSV Files for the Edge Cache

* **Status:** Accepted
* **Date:** 2026-10-02 (Updated)
* **Deciders:** Jude (Lead Engineer)
* **Technical Domain:** Local Storage / Edge Cache Architecture / CLI Data Pipeline

---

## Context and Problem Statement

The Python CLI training engine requires an offline local storage layer (`training-cli`) to persist synced interaction events, track synchronization states (`sync_state`), and log execution metrics (`checkpoint_logs`). Because the system is designed to run efficiently in low-resource environments with unreliable electricity (such as infrastructure-constrained regions), the storage choice must be lightweight, crash-resilient, and capable of handling incremental updates without data duplication or memory bloat.

We need to evaluate our choice of database technology against alternative approaches, comparing native SQLite3 against Python ORMs (like SQLModel) and flat file formats (like CSV/Pandas), while carefully analyzing durability and concurrency settings under sudden power-loss scenarios.

---

## Options Considered

### Option A: SQLModel / SQLAlchemy ORM
Use SQLModel (combining SQLAlchemy and Pydantic) to manage database tables and migrations in Python.

* **Pros:**
  * Pythonic object models with integrated type safety and validation.
* **Cons:**
  * **Heavy Dependency Footprint:** Introduces substantial dependency layers and higher runtime memory overhead, violating the project goal of operating under tight resource constraints.

### Option B: Flat CSV Files Managed via Pandas
Store raw interaction logs and metadata inside local CSV files read and written via Pandas.

* **Pros:**
  * Human-readable and easy to inspect directly as raw text.
* **Cons:**
  * **Memory Inefficiency:** Requires loading entire datasets into RAM during processing instead of streaming data in chunks.
  * **No Native Indexing:** Queries require full-file scans ($O(N)$ complexity).
  * **Concurrency & Atomicity Risks:** Writing updates requires rewriting or appending files, risking file corruption or split-brain states where rows disagree with each other.
  * **Duplicate Vulnerability:** Retrying a failed sync can easily duplicate rows unless complex custom file-checking logic is implemented.

### Option C: Native Lightweight SQLite3 with WAL & Synchronous = NORMAL (Chosen)
Utilize Python's built-in `sqlite3` library with Write-Ahead Logging (WAL) mode enabled (`PRAGMA journal_mode = WAL;`) and `PRAGMA synchronous = NORMAL;`.
* WAL allows SQLite to record changes in a separate log before checkpointing, enabling readers to continue reading while a writer is active (improving concurrency).
* `synchronous = NORMAL` strikes an intentional balance between performance and durability for edge hardware.
* Primary keys on raw interactions mirror unique IDs generated by the NestJS ingestion server to enforce automatic deduplication on sync retries.

* **Pros:**
  * **Zero Extra Bloat:** Uses Python's standard library, minimizing memory and dependency footprint.
  * **High Concurrency & Consistency:** WAL mode ensures readers and writers don't block each other and preserves database structural consistency even after a sudden power loss.
  * **Idempotent Syncing:** Enforcing primary keys mapped directly from server IDs prevents duplicate records during intermittent network retries.
  * **Chunked Processing:** Queries stream records efficiently rather than consuming excessive RAM.
* **Cons:**
  * WAL + `NORMAL` sync does not guarantee absolute zero-data-loss durability; a recently committed transaction can theoretically be lost following a hard power failure if the OS/storage doesn't flush immediately.
  * Requires manual SQL management rather than high-level ORM abstractions.

---

## Decision Outcome

**Chosen Option:** **Option C (Native Lightweight SQLite3 with WAL and Synchronous = NORMAL)**.

Native SQLite3 strikes the ideal balance for an edge cache. While WAL alone doesn't make the cache completely immune to data loss during power cuts, configuring it with `synchronous = NORMAL` preserves overall database consistency and optimizes performance. Because the local store is a cache syncing iteratively from a master server, the risk of losing the absolute last uncheckpointed transaction is an acceptable engineering trade-off compared to the performance penalty of `FULL` synchronization or heavy ORM bloat. However, actual recovery behavior must be validated through testing rather than assumed.

---

## Consequences & Trade-offs

### Positive Consequences
1. **Low Resource Footprint:** Eliminates heavy ORM dependencies, preserving system memory.
2. **Improved Concurrency:** WAL allows simultaneous read and write operations during intensive CLI synchronization loops.
3. **Structural Consistency:** Prevents database file corruption during power cuts or unexpected process termination.
4. **Idempotent Retries:** Primary key mapping protects against duplicate records across flaky network sync cycles.

### Negative Consequences / Risks to Mitigate
1. **Durability Trade-off:** Under sudden power loss with `synchronous = NORMAL`, the very last committed transactions prior to the crash may be lost. If absolute zero-loss durability becomes a strict requirement later, `synchronous = FULL` will need to be evaluated and benchmarked on target edge hardware.

---

## Compliance & Validation

This decision is validated by:
* Implementation of local SQLite schema (`raw_interactions`, `sync_state`, `checkpoint_logs`).
* Explicit SQLite PRAGMA configurations (`journal_mode = WAL`, `synchronous = NORMAL`).
* Smoke tests confirming successful creation of the SQLite cache file and schema tables prior to execution.
