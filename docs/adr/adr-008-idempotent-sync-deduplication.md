# ADR 008: Idempotent Event Synchronization and Local Deduplication via Server-Assigned UUID Primary Keys and UPSERT Semantics

* **Status:** Accepted
* **Date:** 2026-10-09
* **Deciders:** Jude (Lead Engineer)
* **Technical Domain:** Sync Protocol / Data Pipeline / Edge Storage Consistency

---

## Context and Problem Statement

The Python CLI training engine (`training-cli`) incrementally synchronizes user interaction events from the NestJS cloud ingestion server using a hybrid cursor-based delta pagination loop. During synchronization over unstable network connections, transient failures, retry logic, or edge-case cursor overlaps can cause data pages to be delivered or requested more than once.

If the local SQLite cache performs blind insertions (`INSERT INTO interactions ...`), re-delivered pages will create duplicate records. Data duplication in the local cache directly distorts matrix factorization and collaborative filtering models during the offline training phase (`train`).

We need a deterministic, low-overhead deduplication strategy that guarantees idempotency during sync retries without requiring complex client-side state tracking.

---

## Options Considered

### Option A: Blind Append (No Deduplication)
Insert every fetched event row directly into the local SQLite table without checking for existing keys.

* **Pros:** Simplest implementation with maximum insert throughput.
* **Cons:**
  * Leads to severe data duplication upon network retries or overlapping cursor pages, corrupting downstream model training accuracy.

### Option B: Application-Layer Pre-Filtering
Query the local SQLite database for existing event IDs before executing batch insertions, filtering out any IDs already present in memory.

* **Pros:** Prevents duplicate insertions at the application layer.
* **Cons:**
  * Introduces extra round-trip queries and high memory overhead in Python to compare lists of IDs before every batch save.
  * Vulnerable to race conditions if concurrent sync threads are introduced.

### Option C: Database-Level Idempotent UPSERTs using Server-Assigned UUIDs (Chosen)
Map the globally unique `id` generated by the NestJS ingestion server directly as the primary key of the local SQLite `interactions` table. Use SQLite's native upsert clause (`ON CONFLICT(id) DO NOTHING`) during batch execution (`conn.executemany`) to make every page write completely idempotent. Similarly, track sync progression via an upserted `sync_state` table with monotonic timestamp protection (`WHERE excluded.last_sync_timestamp > sync_state.last_sync_timestamp`).

* **Pros:**
  * **Guaranteed Idempotency:** Re-syncing the same page or retrying after a network failure automatically ignores already-persisted records at the storage engine level.
  * **Zero Application Overhead:** Eliminates the need for manual in-memory ID filtering or lookup queries before writing.
  * **Atomic Batch Execution:** `executemany` combined with SQLite transactions ensures that page writes either succeed fully or roll back safely.
  * **Monotonic Cursor State:** The `sync_state` table update condition (`excluded.last_sync_timestamp > sync_state.last_sync_timestamp`) prevents older cursors from accidentally regressing sync progress.
* **Cons:**
  * Requires strict alignment between server-side entity IDs and local primary key definitions.

---

## Decision Outcome

**Chosen Option:** **Option C (Database-Level Idempotent UPSERTs using Server-Assigned UUIDs)**.

By leveraging server-assigned UUIDs as local primary keys and applying `ON CONFLICT(id) DO NOTHING` alongside monotonic cursor updates, the synchronization loop becomes fully idempotent. This protects the local SQLite cache from duplicate pollution during network retries and cursor overlaps.

---

## Consequences & Trade-offs

### Positive Consequences
1. **Resilient Sync Loops:** Network timeouts and automatic retries can be executed safely without risking duplicate training samples.
2. **Data Integrity:** Ensures clean, unique interaction records for the Scikit-Surprise matrix factorization pipeline.
3. **Optimized Performance:** Native SQLite index checks handle conflict resolution efficiently during batch insertions (`executemany`).

### Negative Consequences / Risks to Mitigate
1. **Primary Key Dependency:** The CLI relies entirely on the upstream ingestion server providing stable, unique UUIDs for every interaction event.

---

## Compliance & Validation

This decision is validated by:
* Implementation of `UPSERT_EVENT` using `ON CONFLICT(id) DO NOTHING` in `src/openrec_cli_package/sync.py`.
* Implementation of `UPSERT_CURSOR` ensuring monotonic timestamp updates in `sync_state`.
* Page storage verification logic checking that stored row counts match expected batch footprints.
